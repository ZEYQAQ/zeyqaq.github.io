## 递归查询(Recursive Query)与迭代查询(Iterative Query)

### 一、递归查询(Recursive Query)

递归查询是指当客户端向 DNS 服务器发起查询时,**该服务器必须返回最终的明确结果**(要么是 IP 地址,要么是"无法解析"的错误),而不能让客户端自己再去问别的服务器。

也就是说,客户端把"找到答案"这个任务**完全委托**给了 DNS 服务器,自己只管等结果。

**典型场景:** 客户端(电脑/手机) → 本地 DNS 服务器(如运营商的 DNS、114、8.8.8.8)之间通常采用递归查询。你只问一次,本地 DNS 替你跑完整个流程,最后把答案给你。

### 二、迭代查询(Iterative Query)

迭代查询是指当 DNS 服务器收到查询请求后,如果它自己不知道答案,**不会替你继续追问,而是返回一个"线索"**——告诉你应该去问哪个服务器(返回下一级服务器的地址),然后由发起方自己再去问下一个服务器,如此反复直到得到结果。

**典型场景:** 本地 DNS 服务器 → 根域名服务器 → 顶级域名服务器(.com) → 权威域名服务器之间通常采用迭代查询。

### 两者结合的完整流程

实际中,这两种方式是**配合使用**的。以解析 `www.example.com` 为例:

1. 客户端向本地 DNS 服务器发起**递归查询**("帮我查到底")
2. 本地 DNS 服务器开始迭代查询
   - 问**根服务器** → 根服务器答:"我不知道,但去问 .com 顶级服务器"
   - 问 **.com 顶级服务器** → 答:"去问 example.com 的权威服务器"
   - 问 **example.com 权威服务器** → 答:"IP 是 93.184.x.x"
3. 本地 DNS 服务器把最终 IP 返回给客户端



## 我每次更新dns记录之后，如何保证我的dns解析出来的ip是最新的

**TTL(Time To Live)** 是你在 DNS 记录里设置的一个值(单位:秒),它告诉所有缓存方:"这条记录你最多缓存这么久,到期必须丢弃、重新来问我。"

举例:你给某条 A 记录设了 `TTL = 3600`(1 小时)。

- 某个本地 DNS 在 14:00 查到了旧 IP,会缓存到 15:00。
- 你在 14:10 改了记录。
- 但这台本地 DNS 在 15:00 之前都返回旧 IP,直到缓存过期重新查询,才拿到新 IP。

所以理论上,**全网完全收敛到新 IP 的最坏时间,约等于一个 TTL 周期**（实际还会更久）。

并且更新不生效,往往是因为旧记录藏在很多层缓存里:

1. **权威 DNS 服务器**——这是源头,你改完这里立即是新的。
2. **递归/本地 DNS 服务器**(运营商、8.8.8.8 等)——按 TTL 缓存,是最主要的"延迟来源"。
3. **操作系统缓存**——Windows 的 DNS Client、Linux 的 nscd/systemd-resolved 等。
4. **浏览器缓存**——Chrome 等浏览器自己也有一份 DNS 缓存。



**1. 提前调低 TTL(最重要)。** 如果你计划要改 IP(比如迁移服务器),应该在**改动前几天**就把 TTL 调小,比如从 3600 改成 60 甚至 30。这样等老的高 TTL 缓存全部过期后,后续缓存都只存很短时间,切换时几分钟内就能收敛。切换完成、稳定后再把 TTL 调回较大值以提升性能。

**2. 手动清缓存(只能管自己这一端)。** 在你自己的机器上验证时:

```bash
# Windows
ipconfig /flushdns

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Linux (systemd)
sudo systemd-resolve --flush-caches   # 或 resolvectl flush-caches
```

**3. 直接查权威服务器来验证。** 想确认"源头是否真的改对了",绕过中间缓存直接问权威:

```bash
dig @你的权威DNS服务器 www.example.com
# 对比中间递归返回的结果
dig www.example.com
```

**4. 注意"TTL 之外的额外延迟":**

- 有些递归 DNS(尤其某些运营商)会**无视你的小 TTL**,强行延长缓存,这个你无法控制。
- 如果是修改 **NS 记录**或迁移注册商,顶级域那边的缓存可能涉及更长的固定周期。
