CDN静态资源分发

cdn涉及众多组件，通常一次静态资源的发布链条是：

git仓库-（编译构建）-静态资源产物-（上传）-存储桶-（CDN边缘节点加速）-用户浏览器

所以有几个需要明确的点：

1、CDN资源本质上存在于底层对象存储中。通常这些存储桶按照区域（Region）来划分。

2、为了明确存储桶的管理和域名的归属和权限计费，通常使用CDN业务线来做上层的划分。

3、一个区域可以管理多个存储桶，但是必须存在一个主桶，后续前端项目构建会根据主桶来给构建环境注入对应环境变量。

4、CDN需要有规范的业务线域名，如https://{CDN_DOMAIN}/obj/{BUCKET_NAME}（一般公有云不会暴露出桶名，这里只是举例）/{PUBLIC_PATH}/{FILE_PATH}。

在前端工具如Webpack / Vite / Modern.js / EdenX 等在构建时，需要将资源引用的前缀指向CDN的地址，所以需要在构建配置中将 output.publicPath 或 assetPrefix 设为对应的环境变量。

对于前端产物而言，我们通常默认产物目录是output/resource 或dist，并且还需要忽略node_modules等非静态资源目录，以保障产物大小＜5GB。构建完成后会调用上传服务将资源分发至配置好的各区域存储桶。

cdn的报错常常和跨域相关，如果console报错Access-Control-Allow-Origin 跨域拦截，则需要检查是否在<script> 或资源请求中误加了 crossorigin="use-credentials"，这样的情况下浏览器会要求精确的 Origin 匹配，导致通配符 * 失效。解决：移除use-credentials 即可。

cdn构建时读不到海外CDN域名则会报错环境变量缺失，比如CDN_OUTER_SG 为空，这需要到CDN业务线Bucket设置里加入对应区域为主要Bucket。如果没有这个区域的桶那就新建。

如果构建成功但是线上404，很可能是路由/代码声明的静态资源路径与 SCM 打包出的实际路径不一致，或者文件未被打进产物包。需要下载产物解压来核对文件真实相对路径与 publicPath 拼接后是否一致。

如果在CDN上传时报错403，这常常是因为业务桶使用了安全校验机制，或者某种特定类型文件并没有在桶策略加白，这时只能优先联系对应人员解禁，或放开对应后缀文件的上传。

若采用 Hash 文件名发布，通常不会有老缓存问题；如果访问到旧资源，大概率是 HTML 入口文件被错误设置了强缓存，或者发布了非 Hash 的同名覆盖资源导致边缘节点 TTL 未过期。

上传至外网时常常超时，这时可以使用API触发上传。

CDN为什么快？DNS解析到请求最近的边缘节点，边缘节点检查是否自己存有这份文件，如果没有则去存储桶源站拉取，分发给用户的同时也自己留存一份，后续再收到相同 URL 的请求，则直接从本地缓存返回。（cdn资源一般以hash为文件名，这样只要有发版，文件引用的url就会变）

更狠的是预热（Warm-up）功能，在每次发布静态资源之后，CDN会主动从存储桶把最主要的几个指定文件（一般是index.html）拉取并分发给核心边缘节点。

为什么是核心边缘节点而不是全部的？因为实际上CDN边缘网络是分层的，在离用户最近的L1边缘节点实际上资源容量相对优先，主要缓存了最热的头部资源，没命中的资源会请求到L2区域的汇聚节点。这样设计避免了频繁对存储桶源站的访问，保护源站不被击穿。同时CDN会给那些热门url加上互斥锁，只放行第一个请求去回源，其余并发请求挂起，待数据拉回后一次性响应。

即使这样，流量也很贵，我们常常这样在HTTP Header中配置

Cache-Control: public, max-age=31536000, immutable

max-age=31536000代表了，一年之内（当然这里略显夸张），不要再向服务器发验证请求，直接使用本地缓存。

immutable代表了，即使用户使用了普通刷新，也不会向服务器发验证请求，直接使用本地缓存。

ETag: "5d8c72-3c8"

"5d8c72-3c8"是这个文件的哈希值，目的就是保证，每一份文件（即使同名）在网站发版后仍然是最新的，而不是取到同名旧资源，也不覆盖同名文件。

TikTok如何做到丝滑秒播？

虽然视频存放在 CDN 上，但TikTok并不是等用户滑到某个视频时才临时去下载整个视频，而是通过预加载在你上一次使用TikTok时就下载好了本次要看的内容。同时，TikTok还会在后台向CDN请求接下来的几个视频的前几秒数据。针对用户当前的网速，TikTok甚至用上了自适应码率和自适应编码格式，力求就算视频糊也丝般顺滑。
