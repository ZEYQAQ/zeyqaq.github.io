一种存活探针的特殊解决方案

当前场景：

需要对一组工作负载配置存活、就绪、启动探针。

绝大多数由Spring框架写的Java城程序都在对外端口的/health处预留了标准的健康检查。

即：只需要配置

spec:
  template:
    spec:
      containers:
        - name: Podname
          livenessProbe:
            httpGet:
              path: /health
              port: 8787
              scheme: HTTP
            timeoutSeconds: 1
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health
              port: 8787
              scheme: HTTP
            timeoutSeconds: 1
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3
          startupProbe:
            httpGet:
              path: /health
              port: 8787
              scheme: HTTP
            timeoutSeconds: 1
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3

当前存在一个文件服务器，要求实现对其进行健康检查，我们的一位老同事的解决方案是：

首先，我们的文件服务器对外暴露的逻辑是wget /ip/fileserver/<文件>
而为了保障其正常运行，我的同事在服务器中放了一个a.txt文件，里面写了123
他的想法是通过curl这个/ip/fileserver/a.txt来得到123，如果文件不存在或者取不到则证明服务异常。

那么在k8s中的存活探针则配置：
livenessProbe:
            httpGet:
              path: /fileserver/a.txt
              port: 8100
              scheme: HTTP
            timeoutSeconds: 1
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3

但是当我将文件删除之后，健康检查仍返回正常：

rm -f a.txt

curl http://localhost:8100/fileserver/a.txt
{"description":"file is not exist.","status":"success"}

原因是：健康检查逻辑只认status，无关其他内容。所以这个探针属于歪打正着：无需关注a.txt的具体内容，当文件服务挂掉后健康检查也会正常重启进程：

ps aux

由于当前vibe coding的深入，常常出现一些错误，比如每次启动再从服务器拉包。这听起来确实很不合逻辑，但是生产环境确实发生了。那么要监控这种服务启动时长较长的容器，就要用好就绪和启动探针：

这里可以将启动探针的/health的检测周期(s)调为120s（PS：一个较大的数值），最大失败次数为3。这样可以尽可能避免容器还没启动而被k8s杀掉，再重启再杀掉的循环。

而存活探针可以正常配置，因为一旦启动，就可以正常探测。

#存活探针规格可参考：
检测周期(s) 10	
延迟时间 (s) --
超时时间 (s) 1	
成功阈值 1	
最大失败次数 3

如果批量测试健康检查，可以这样

kubectl get pods |awk {'print $1'}

#!/bin/bash
# batch-kill1.sh
# 批量对指定 Pod 执行 kill 1（优雅触发容器重启）
# 使用方法: ./batch-kill1.sh [namespace]
# 默认 namespace 为 default

set -u

NAMESPACE="${1:-default}"

PODS=(
  <这里是你刚刚得到的PODs>
)

SUCCESS=()
FAILED=()

echo "==> 目标 namespace: ${NAMESPACE}"
echo "==> 共 ${#PODS[@]} 个 Pod，将依次执行 kill 1"
echo

for POD in "${PODS[@]}"; do
  echo "----> [$(date '+%F %T')] 处理 Pod: ${POD}"
  if kubectl exec -n "${NAMESPACE}" "${POD}" -- /bin/sh -c "kill 1" 2>/dev/null; then
    echo "     ✔ 已发送 kill 1"
    SUCCESS+=("${POD}")
  else
    # kill 1 会导致容器 PID1 退出，exec 通道常常随之中断返回非 0
    # 这里再探测一次 Pod 是否进入 Terminating/Restart 状态
    STATUS=$(kubectl get pod -n "${NAMESPACE}" "${POD}" -o jsonpath='{.status.phase}' 2>/dev/null || echo "NotFound")
    if [[ "${STATUS}" == "Running" || "${STATUS}" == "Pending" || "${STATUS}" == "NotFound" ]]; then
      echo "     ⚠ exec 返回非 0，但 Pod 状态=${STATUS}，通常为 PID1 被杀导致连接中断，视为成功"
      SUCCESS+=("${POD}")
    else
      echo "     ✘ 失败 (状态=${STATUS})"
      FAILED+=("${POD}")
    fi
  fi
  echo
done

echo "================ 执行结果汇总 ================"
echo "成功 (${#SUCCESS[@]}):"
printf '  - %s\n' "${SUCCESS[@]}"
if (( ${#FAILED[@]} > 0 )); then
  echo "失败 (${#FAILED[@]}):"
  printf '  - %s\n' "${FAILED[@]}"
  exit 1
fi
echo "全部完成 ✅"

运行在配置有对应集群的kubectl执行机上，会kill掉由Java写的程序（因为一般java程序的PID为1）。

观测指标

increase(  kube_pod_container_status_restarts_total{

      namespace=~"default",

      cluster=~"<cluster_id>"

    }[180s] )

由于k8s的存活探针是会自动重启pod，所以过后告警即可恢复。（这里是increase( )）

为什么是 [180s] ？

kube_pod_container_status_restarts_total 是一个累计计数器，kube-state-metrics 默认每 30s~1min 才抓取一次。

increase([60s]) 只看最近 60 秒内的样本点，如果这段时间内只采集到 1 个点（甚至 0 个），Prometheus 就没有足够的数据计算增量，结果为 0。
